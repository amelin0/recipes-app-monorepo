# Аудит гонок і транзакцій

> Частина [журналу бекенду](../HANDOFF.md).

Правило власника: кожен read-then-write має витримувати паралельні запити;
справжній захист — обмеження в базі, умовний `UPDATE` чи блокування рядка, а
не перевірка в сервісі; ізоляцію обирати свідомо; зовнішні події —
ідемпотентні. «Задокументована гонка» — не кінцевий стан.

**Спільна причина більшості знахідок:** `BaseRepository` тримає лише
`this.db`, тож багатокрокові сценарії сервісів — це послідовні автокоміти на
`READ COMMITTED` (чек, код, ротація, скидання пароля, блокування, онбординг).
Ізоляцію ніде не обрано. Плюс `GlobalExceptionFilter` перетворює будь-яку
помилку Postgres на 500 — кожна гонка, яку спіймав констрейнт, доходить до
користувача 500-кою (треба `23505 → 409`, `23503 → 404/409`).

Напрям виправлення без нового фреймворку: багатокроковий сценарій стає
**одним методом репозиторію з власною транзакцією** — так уже працюють
`createAccount`, `copyDay`, `grantReferralReward`.

**Виправлення** — п'ять паралельних гілок, розведених за файлами. Кожна
змінювала лише схему; міграції генеруються під час інтеграції по черзі, тож
гілки інтегруються **лінійним стеком** поверх #20 (номери міграцій — у цьому
порядку).

**Пункт 3 (перезапис пароля при повторній реєстрації) закрито частково.**
Закрито: запис після верифікації, зміну пароля без перевіреного коду,
захоплення через «Продовжити з Google». Лишилось: реєстрація, що прийшла
**після** власника, замінює його код — і якщо власник введе найновіший код,
паролем стане пароль того, хто зареєструвався пізніше. Повністю закривається
лише зміною контракту: `/register` віддає nonce, який `/verify-email` мусить
повернути. **Потрібне рішення власника й тіммейта** — це зміна для мобілки.

**Вікно пільги для refresh — затверджено власником 2026-09-11 як тимчасове
(«поки ок»).** Атомарна ротація refresh-токенів зробила б два одночасні
refresh застосунку схожими на повтор і розлогінювала б людину. Тому в
клієнтський API додається вікно пільги, як в адмінці, **але обмежене однією
сестринською парою**: мобілці нічого міняти не треба, а третій запит у вікні
вже вважається повтором. Коли застосунок серіалізуватиме refresh сам (як
веб-панель), вікно можна прибрати — питання лишається відкритим.

**Дедуплікація вебхуків магазинів** (коли з'являться App Store Server
Notifications / Google RTDN):

- журнал вхідних `store_notifications` із `PRIMARY KEY (store, notification_id)` —
  `INSERT … ON CONFLICT DO NOTHING RETURNING`, дубль → 200 і стоп;
- підписка ключується довгоживучим id магазину
  (`store_original_transaction_id` / `purchase_token`) з `UNIQUE`, зміни — під
  `FOR UPDATE`, захист від доставки не за порядком через `last_event_at`;
- грошовий журнал `store_transactions` з `UNIQUE (store, transaction_id)` —
  кожен перевірений чек і повернення потрапляють туди ідемпотентно;
- у `notifications` — `dedupe_key` з частковим унікальним індексом
  `(user_id, dedupe_key)`: `emit` пише `ON CONFLICT DO NOTHING` (закриває й
  пункти 12–13).
