# Виконати прострочені запити на видалення акаунту

> **Це тимчасова ручна процедура.** Завдання, яке має робити це автоматично,
> ще не написане, бо спершу треба ухвалити
> [ADR-0005](../adr/0005-what-account-deletion-erases.md). Доки його немає,
> прострочені запити накопичуються і **нічого не відбувається саме собою**.

## When to use this

Запускати **щотижня**, а також негайно, якщо:

- користувач скаржиться, що просив видалити акаунт понад 30 днів тому, а той
  досі працює;
- надійшов формальний запит на видалення персональних даних (GDPR / NPD);
- запит нижче показує ненульову кількість.

```sql
SELECT count(*)
FROM account_deletion_requests
WHERE cancelled_at IS NULL
  AND executed_at IS NULL
  AND scheduled_for <= now();
```

**Сигнал у моніторингу тепер є.** Погодинне завдання воркера рахує відкриті
запити й публікує три ряди:

- `dns_account_deletion_requests_open{state="overdue"}` — скільки прострочено;
- `dns_account_deletion_requests_open{state="waiting"}` — скільки ще
  відлічують строк;
- `dns_account_deletion_requests_oldest_overdue_seconds` — скільки чекає
  найстаріший.

Алерт `dns-overdue-account-deletions` дивиться на **вік**, а не на кількість:
доки процедура ручна й тижнева, ненульова кількість — нормальний стан у
вівторок, і алерт на неї спрацьовував би щотижня. Поріг — 10 днів, тобто
«тижневий запуск пропустили». Процедура лишається календарною; алерт — це
страховка на випадок, коли календар не спрацював.

Якщо алерт спрацьовує регулярно — це аргумент дописати
[ADR-0005](../adr/0005-what-account-deletion-erases.md) і зробити завдання
автоматичним, а не підняти поріг.

## Prerequisites

1. Доступ до продакшен-бази (`DATABASE_URL`) і право виконувати `DELETE`.
2. Свіжий бекап бази **не старший за годину**. Процедура незворотна.
3. Підтверджений [ADR-0005](../adr/0005-what-account-deletion-erases.md) —
   або, якщо він досі `Proposed`, письмове погодження власника продукту на
   жорстке видалення (див. «Обмеження» нижче).
4. `psql` або інший клієнт, що вміє транзакції.

## Обмеження чинної схеми

Сьогодні всі таблиці посилаються на `users.id` з `ON DELETE CASCADE`, тож
доступна **лише** одна поведінка: стерти геть усе. Це збігається з тим, що
ADR-0005 пропонує для персональних даних, але **не** зберігає фінансових
записів — їх поки просто немає, бо домену subscription не існує.

Практично це означає: поки не зʼявилися підписки, жорстке видалення безпечне.
Щойно вони зʼявляться — цю процедуру не можна виконувати, доки ADR-0005 не
ухвалено і схему не приведено до нього. Перевірити просто:

```sql
SELECT to_regclass('public.subscriptions');
```

Якщо результат **не** `NULL` — зупинитися і йти до автора ADR-0005.

## Steps

1. **Переконатися, що бекап свіжий.** Без цього далі не йти: кроки нижче
   незворотні.

2. **Подивитися, кого саме це торкнеться.** Спершу очима, потім видаляти.

    ```sql
    SELECT r.id AS request_id, r.user_id, u.email, r.created_at, r.scheduled_for
    FROM account_deletion_requests r
    JOIN users u ON u.id = r.user_id
    WHERE r.cancelled_at IS NULL
      AND r.executed_at IS NULL
      AND r.scheduled_for <= now()
    ORDER BY r.scheduled_for;
    ```

    Очікуваний вивід: рядки, де `scheduled_for` у минулому. Якщо рядків немає —
    процедура закінчена, нічого робити не треба.

3. **Перевірити, чи не зʼявилися фінансові таблиці** (див. «Обмеження»):

    ```sql
    SELECT to_regclass('public.subscriptions');
    ```

    Очікуваний вивід: `NULL`. Будь-що інше — **зупинитися**.

4. **Видалити в транзакції.** `ON DELETE CASCADE` прибере профіль,
   налаштування, нагадування, токени, коди, OAuth-звʼязки і сам запит на
   видалення. `executed_at` проставляти нема куди — рядок запиту зникає разом
   з користувачем, тож фіксувати факт треба поза базою (крок 5).

    Звернення в підтримку (`feedback`) навмисно **не** каскадяться: за
    ADR-0005 вони знеособлюються, а не зникають. Каскад `SET NULL` сам обнуляє
    `user_id`, але **не** `reply_email` — його доводиться стирати явно, інакше
    особиста адреса того, хто попросив видалити свої дані, лишиться в базі.
    Перевірено 2026-09-06: без цього рядка адреса переживає видалення.

    ```sql
    BEGIN;

    -- Знеособити звернення ДО видалення: після нього зв'язок втрачено
    -- і знайти потрібні рядки вже не буде як.
    UPDATE feedback
    SET reply_email = NULL
    WHERE user_id IN (
        SELECT user_id
        FROM account_deletion_requests
        WHERE cancelled_at IS NULL
          AND executed_at IS NULL
          AND scheduled_for <= now()
    );

    -- Стільки рядків має бути видалено, скільки показав крок 2.
    DELETE FROM users
    WHERE id IN (
        SELECT user_id
        FROM account_deletion_requests
        WHERE cancelled_at IS NULL
          AND executed_at IS NULL
          AND scheduled_for <= now()
    );

    -- Звірити кількість із кроком 2, і лише тоді:
    COMMIT;
    ```

    Якщо кількість не збігається — `ROLLBACK;` і розібратися, перш ніж
    повторювати.

5. **Записати факт виконання** — дату, кількість видалених акаунтів і хто
   виконував — у журнал операцій команди. Рядків у базі після кроку 4 не
   лишається, тож це єдиний слід того, що вимогу виконано.

## Verification

Запит із розділу «When to use this» має повернути `0`.

Додатково — жодного осиротілого рядка не лишилося (усі мають повертати `0`):

```sql
SELECT
    (SELECT count(*) FROM profiles      p LEFT JOIN users u ON u.id = p.user_id WHERE u.id IS NULL) AS orphan_profiles,
    (SELECT count(*) FROM user_settings s LEFT JOIN users u ON u.id = s.user_id WHERE u.id IS NULL) AS orphan_settings,
    (SELECT count(*) FROM refresh_tokens t LEFT JOIN users u ON u.id = t.user_id WHERE u.id IS NULL) AS orphan_tokens;
```

Жодне знеособлене звернення не тримає адреси для відповіді (має бути `0`):

```sql
SELECT count(*) AS tickets_with_email_but_no_author
FROM feedback
WHERE user_id IS NULL AND reply_email IS NOT NULL;
```

Спроба увійти під видаленою адресою має дати `401 auth.invalid-credentials` —
тобто рівно те саме, що й неіснуюча адреса.

## Rollback

**Відкату немає.** Після `COMMIT` на кроці 4 дані відновлюються лише з бекапу,
і це відновить **усю** базу на момент бекапу, а не окремі акаунти — тобто
відкотить і роботу всіх інших користувачів за цей час.

Саме тому крок 1 обовʼязковий, а крок 4 виконується в транзакції зі звіркою
кількості перед `COMMIT`.

Якщо помилка виявилася **до** `COMMIT` — `ROLLBACK;`.

## Історія перевірок

- **2026-09-06** — прогін на **локальній** базі (`docker compose`), не на
  продакшені. Фікстура: три акаунти, один прострочений запит, один скасований.
  Підтверджено: крок 2 показує рівно прострочений; крок 3 повертає `NULL`;
  крок 4 видаляє один рядок; перевірка дає `0` прострочених і `0` осиротілих;
  вхід під видаленою адресою віддає побайтово ту саму відповідь, що й під
  неіснуючою; скасований запит і сторонній акаунт лишаються недоторканими.
- **2026-09-06, друга ітерація** — після появи звернень у підтримку виявлено,
  що `DELETE FROM users` лишає в `feedback.reply_email` особисту адресу
  видаленого користувача: каскад `SET NULL` обнуляє `user_id`, але не колонку
  з адресою. Відтворено на локальній базі (адреса пережила видалення), додано
  крок знеособлення в крок 4 і відповідну перевірку; після виправлення
  контрольний запит дає `0`.
