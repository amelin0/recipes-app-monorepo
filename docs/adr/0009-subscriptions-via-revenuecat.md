# ADR-0009: Магазини підключаємо через RevenueCat; право доступу вирішує наш сервер по дзеркалу, а не SDK

> Вибір RevenueCat — рішення власника продукту від 2026-09-13. Усе інше в
> цьому документі — як саме його вбудувати — пропозиція, що чекає на
> підтвердження власника й автора бекенду. Контракт для бекенду —
> `TODO_BE.md`, §10; налаштування дашбордів — рунбук
> [`configure-revenuecat`](../runbooks/configure-revenuecat.md).

## Context

Домен підписки досі закінчується там, де починається магазин.
`POST /subscription/receipt` бере чек «на віру» (`PurchasesService` — stub,
гілки Apple і Google відповідають `503`), у мобільному застосунку немає
жодного IAP-модуля, а тап по платному плану показує тост «Оплата через App
Store буде доступна у наступній збірці». Усе решта — плани, один живий рядок
`subscriptions` на акаунт із частковим унікальним індексом, блокування
акаунта, перенесення подарованих днів поверх купленого, реферальні місяці й
винагорода рефереру — працює і покрите тестами.

Тепер продукт додає замки
([`client/subscription/free-tier`](../specs/client/subscription/free-tier/spec.md)):
частина рецептів, четверта власна страва, імпорт плану в список, копіювання
раціону, замкнена страва в плані, статистика прогресу. Кожній замкненій дії
потрібна швидка і надійна відповідь «чи є право», і давати її має **сервер**
— прихована кнопка не захист (free-tier FR-017).

Що ми знаємо про магазини і про RevenueCat (перевірено по документації
Apple і RevenueCat 13.09.2026; джерела — у дослідженні до цього ADR):

- **Пряма інтеграція** — це App Store Server API + Server Notifications V2
  (Apple дозволяє один URL на середовище), а потім Google Play Developer API
  + Pub/Sub: дві криптографії чеків, два набори кредів, і жодного з них у нас
  досі немає.
- **RevenueCat** бере це на себе: SDK у застосунку фінішить транзакції,
  бекенд RC валідує їх (для StoreKit 2 обовʼязковий In-App Purchase Key з
  App Store Connect), шле нам вебхуки і віддає стан клієнта через
  `GET /v1/subscribers/{id}`. RC сам радить після кожного вебхука
  **перечитати стан**, а не застосовувати payload: доставка «принаймні один
  раз», порядок не гарантований, після пʼяти невдалих спроб (≈2,6 год)
  подія губиться.
- **Промо-гранти RC** («granted entitlements») не складаються з платною
  підпискою: вони йдуть паралельно, пізніша дата виграє, другий грант на
  активний відхиляється, події гранту завжди `PRODUCTION`, ревокація як
  вебхук не задокументована. Тобто «місяць рефереру, у якого вже є річна»
  через RC — місяць викинутий, а рішення власника від 2026-09-11 («зароблені
  дні переносяться поверх купленого») RC виразити не може.
- **Restore behavior** проєкту за замовчуванням — «Transfer to new App User
  ID»: одна підписка Apple ID належить одному акаунту RC одночасно; про
  перенесення дізнається лише переможець (`TRANSFER`), програвший не отримує
  `EXPIRATION`.
- **Trusted Entitlements** — захист SDK від підміни відповіді на пристрої,
  інформаційний; до серверної авторизації стосунку не має.
- Мобільна збірка — `expo-dev-client` з закоміченим `ios/`, TestFlight
  збирається руками в Xcode. `react-native-purchases` (10.x) не має
  config-плагіна Expo і не потребує `prebuild`: `pod install` і перезбірка.

## Decision

1. **Магазини — через RevenueCat, не напряму.** Мобілка — ядро
   `react-native-purchases` без готових пейволів RC (пейвол свій, у
   `view/subscription/paywall/`); `appUserID = users.id`, конфігурується один
   раз після відновлення сесії, `logOut()` не викликається (зміна акаунта —
   `logIn`). Один проєкт, один App Store-app, один entitlement `pro` на
   обидва продукти, offering `default` з двома пакетами.
2. **RevenueCat — правда про покупки; наш сервер — правда про доступ.**
   `client-api` приймає вебхук `POST /webhooks/revenuecat` (заголовок
   авторизації + HMAC, ідемпотентність по `event.id`) і лише **записує**
   подію: таблиця `revenuecat_events` — це outbox, обробляє воркер. Обробка
   — завжди перечитування `GET /v1/subscribers/{id}` секретним ключем і
   зведення результату з живим рядком `subscriptions` **під тим самим
   блокуванням акаунта і за тими самими правилами**, що сьогодні
   застосовуються до чека (заміна з перенесенням подарованого), плюс
   «оновити на місці» для grace і «закрити/скоротити з перенесенням» для
   повернень і перенесень. Гасити доступ можна лише на позитивних доказах
   від RC (дата минула, refund, `TRANSFER`) — нечитабельна відповідь
   нічого не змінює. `CustomerInfo`, який приносить клієнт, не
   приймається ніколи. Кожен гейт читає лише живий рядок — жодного виклику
   RC і жодного кешу на шляху запиту.
3. **Реферальний місяць, місяць-винагорода і ручний грант із дашборду RC —
   локальні рядки** (`source=referral`, `store=none`); перші два в RC не
   потрапляють. Доступ живе лише на рядку `active`: коли магазинний рядок
   закривається (refund, перенесення), подарований залишок переїжджає в
   новий локальний рядок, а не лишається на `cancelled`, якого `findActive`
   не бачить. Наслідок для застосунку: замки читаються з
   `GET /subscription`, а не з `entitlements.active` SDK — для реферального
   користувача SDK каже «без підписки», і це правильно з погляду RC.
4. **Пробіл між покупкою і вебхуком** (5–60 с) закриває `POST
   /subscription/sync`, який застосунок кличе одразу після покупки чи
   відновлення; коли RC не відповів за 5 с, він повертає `200` зі станом
   «активуємо», а не помилку — людині, яка щойно заплатила, `5xx` не
   відповідаємо. **Втрачені вебхуки** добирає воркер-звірка (ADR-0008) по
   рядках біля дати закінчення і по дзеркалу, яке каже «оплачено» там, де
   рядка немає.
5. `POST /subscription/receipt`, `submitReceiptSchema`, `PurchasesService` і
   креди `APPLE_ISSUER_ID`/`APPLE_KEY_ID`/`APPLE_PRIVATE_KEY`/
   `GOOGLE_SERVICE_ACCOUNT_JSON` прибираються. `POST /subscription/redemptions`
   не змінюється.
6. Restore behavior лишаємо «Transfer to new App User ID»; `TRANSFER`
   обробляємо ресинком обох сторін.
7. Sandbox- і TestFlight-періоди пишуться в дзеркало завжди, а доступ дають
   лише під `REVENUECAT_ENTITLE_SANDBOX` — `true` до релізу, `false` після.
8. Режим `stub` — явний (`REVENUECAT_MODE`), не «вивід з відсутності
   ключа»: у проді без `live` сервер не стартує. Інакше одна забута змінна
   робила б `POST /subscription/sync` роздачею Premium.
9. Конверсія для реферальної винагороди — за датою **першої** покупки
   підписки в магазині (`original_purchase_date`) і лише після платного
   рядка в журналі: підписка, перенесена між власними акаунтами через
   restore, і grace після невдалої конверсії trial місяця рефереру не
   дають. Без унікального чека це єдине, що тримає правило «не нафармити».

## Consequences

- ✅ Жодного парсингу чеків і жодних кредів магазинів у нас. Android пізніше
  — той самий вебхук і той самий ресинк, лише другий публічний ключ у
  застосунку і креди Google у дашборді RC.
- ✅ Модель `subscriptions` — один живий рядок, індекс, блокування,
  перенесення подарованих днів, винагорода рефереру — і її тести лишаються.
  Змінюється лише те, хто пише магазинний період: ресинк замість чека.
- ✅ Гейт — один індексований запит до нашої бази. RC може лежати годину —
  доступ від цього не зникає, і нові покупки за цей час доберуться вебхуком
  або звіркою.
- ✅ Добирання винагород, що зірвалися (referral plan, «Що ще не
  побудовано»), стає природним: кожен ресинк кличе ідемпотентний
  `rewardReferrer`.
- ⚠️ **Дві правди на межі.** Для RC реферальний користувач — без підписки:
  дашборд RC не покаже подарованих місяців, SDK-шний `isActive` для нього
  хибний, і будь-хто, хто колись загейтить по `CustomerInfo`, зламає
  реферальну програму. Правило «замки — лише по `GET /subscription`» живе в
  `apps/mobile/CLAUDE.md`, а не лише тут.
- ⚠️ Стан eventually consistent: поновлення без вебхука видно через ≤30 хв
  (звірка) або одразу після `sync` із застосунку; біля дати закінчення замок
  може блимнути на один запит. Збій RC довший за годину — покупки за цей
  час доберуться ретраями outbox і звіркою, доступу в них немає, доки RC
  не відповість.
- ⚠️ iOS 15 (deployment target 15.1) іде через StoreKit 1, для якого RC
  вимагає App-Specific Shared Secret; або додаємо секрет, або піднімаємо
  target до 16.0 — пропозиція друга (`TODO_BE.md` §10.15).
- ⚠️ Залежність від зовнішнього сервісу з платними планами і лімітами API
  (v1 — недокументовано, ~1 запит/с; v2 — 480/хв на домен). Секрет `sk_` —
  ще один ключ у продовому оточенні, а вебхук — перший публічний ендпоінт
  без JWT.
- 💸 Правило заміни в репозиторії доповнюється гілкою «скоротити»
  (повернення коштів, `TRANSFER`) — сьогодні «чек ніколи не коротшає».
  Тести `redeemReceipt` переписуються на підставлену відповідь
  `GET /subscribers`; самі правила ті самі.
- 💸 Дві нові таблиці (`revenuecat_events` як outbox, `revenuecat_customers`
  як дзеркало), колонки `billed_until`/`store_original_purchase_at` на
  `subscriptions`, три задачі воркера, винесення `rewardReferrer` у
  спільний сервіс, stub із тим самим швом для стенду й тестів.
- 💸 Пейвол мусить дорости до вимог App Review (3.1.2, Schedule 2 §3.8(b)):
  «Відновити покупки», посилання на умови і політику приватності на самому
  екрані, сума списання як найпомітніша ціна. У макетах цього немає (paywall
  FR-018).

## Alternatives considered

- **Пряма інтеграція App Store Server API + Server Notifications V2, потім
  Google.** Відхилено: дві реалізації верифікації, два вебхуки, JWS Apple і
  Pub/Sub Google — місяці роботи на те, що RC дає за один ключ, і все одно
  довелося б будувати те саме дзеркало.
- **RevenueCat — єдина правда і про доступ; реферальні місяці — промо-гранти
  RC.** Відхилено: гранти не складаються з платною підпискою і не
  відкладаються — місяць рефереру з живою річною пропав би; другий грант на
  активний відхиляється; події грантів завжди `PRODUCTION`; ревокація без
  задокументованого вебхука. Порушує referral FR-006 і рішення 2026-09-11.
- **Гейтити на клієнті по `CustomerInfo` (з Trusted Entitlements).**
  Відхилено: це захист від підміни на пристрої, не авторизація; free-tier
  FR-017 вимагає відмови сервера; і `CustomerInfo` нічого не знає про
  реферальні місяці.
- **Застосовувати стан із payload вебхука (`INITIAL_PURCHASE` → active,
  `EXPIRATION` → expired) без перечитування.** Відхилено: порядок не
  гарантований, `BILLING_ISSUE` не означає закінчення, `TRANSFER` не шле
  `EXPIRATION` програвшому, і RC сам радить перечитувати.
- **Дзеркало в окремій таблиці, а `subscriptions` — лише локальні гранти;
  право = `max()` двох.** Відхилено: перенесення подарованих днів поверх
  купленого вимагає саме того злиття, яке `redeemReceipt` уже робить;
  `max()` поглинав би реферальний місяць.
- **Restore behavior «Keep with original App User ID».** Відхилено: другий
  акаунт на тому ж Apple ID отримує помилку не лише на відновленні, а й на
  новій покупці — повторний вхід перетворюється на помилку оплати.
- **Окремий RC-app «для стейджингу».** Відхилено: ризик відвантажити
  застосунок із тестовим ключем; замість цього `environment` на рядку і
  env-перемикач.
