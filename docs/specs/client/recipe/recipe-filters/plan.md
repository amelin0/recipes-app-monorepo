# Plan: Recipe filters (Фільтри рецептів)

## Summary

FR-002, FR-003, FR-004, FR-006, FR-007 і FR-008 — серверна частина: один
ендпоінт `GET /recipes/filters` з усіма пʼятьма групами і діапазоном, та
семантика поєднання умов у `GET /recipes`. FR-001 і FR-005 клієнтські
(навігація, кнопка «Скинути всі фільтри»).

Власних таблиць не додає — читає довідники з
[`../recipes-list/plan.md`](../recipes-list/plan.md).

FR-007 більше не `[NEEDS CLARIFICATION]`: семантику зафіксовано
[ADR-0006](../../../../adr/0006-products-absorb-ingredients.md) і
реалізовано так, як там записано.

## API contract

### `GET /recipes/filters`

**Auth:** `JwtGuard`

**Response 200:**

```json
{
    "data": {
        "quickProducts": [{ "id": "…", "name": "Шпинат", "caloriesPer100g": 23, "servingWeightG": null }],
        "categories": [{ "id": "…", "slug": "salty-breakfast", "emoji": "🥓", "imageUrl": null, "name": "Солоні сніданки" }],
        "productGroups": [{ "id": "…", "slug": "vegetables", "emoji": "🥦", "name": "Овочі" }],
        "cuisines": [{ "id": "…", "slug": "italian", "emoji": "🇮🇹", "name": "Італійська" }],
        "diets": [{ "id": "…", "slug": "vegan", "emoji": "🌱", "name": "Веганська" }],
        "calories": { "min": 0, "max": 800, "step": 10 }
    }
}
```

**Усі пʼять груп і діапазон одним запитом.** Екран показує їх одночасно;
пʼять поїздок на сервер заради одного екрана — той самий водоспад, від якого
клієнт побудований тікати.

**Опції мають `id` і `slug` водночас.** `id` клієнт відправляє назад у
фільтр, `slug` — те, чим код і аналітика називають опцію. Показувати треба
`name`, і він уже мовою читача.

**Швидкі інгредієнти — це продукти, а не окремий словник.** FR-002 називає
пʼятнадцять поіменно, і кожен із них має бути тим самим рядком, що й у
пошуку та у складі рецепта. Позначає їх `products.is_quick_pick`.

### Семантика поєднання (FR-007)

| Група                     | Всередині групи | Як реалізовано                          |
| ------------------------- | --------------- | --------------------------------------- |
| Категорії                 | **OR**          | `category_id IN (…)`                    |
| Кухні                     | **OR**          | `cuisine_id IN (…)`                     |
| Дієти                     | **OR**          | один `EXISTS` з `diet_id IN (…)`        |
| Інгредієнти (продукти)    | **AND**         | окремий `EXISTS` на кожен обраний       |
| Групи продуктів           | **AND**         | окремий `EXISTS` на кожну обрану        |
| Діапазон калорій          | завжди AND      | `calories / greatest(servings,1)`       |

Між групами — завжди AND.

**Асиметрія навмисна.** Групи «вмісту» перетинають множини, групи
«належності» їх обʼєднують. Однакове правило для всіх пʼяти виглядало б
охайніше, але одна з двох його версій завжди неправильна: AND по кухнях не
поверне нічого ніколи, OR по інгредієнтах перетворить «курка і рис» на
«курка або рис».

**Ціна цієї асиметрії видима в запиті:** групи «вмісту» вимагають окремого
підзапиту на кожну обрану опцію, групи «належності» — одного `IN`.

### Діапазон калорійності

Рахується **на порцію** — `calories / greatest(servings, 1)` — бо зберігається
число на всю страву (див. план каталогу). Ділення в запиті, а не в другій
збереженій колонці, яка вільна розійтися з першою.

`caloriesMax = 800` означає «800+», тобто **умова не додається**. Верх
повзунка підписаний саме так, і запит, притиснутий до максимуму, не має
ховати кожну ситнішу страву.

**Діапазон не рахується в лічильнику активних фільтрів** — це вимога
`recipes-list` FR-007, і сервер її не порушує, бо лічильника не веде: він
клієнтський, як і чипси.

### Живий лічильник результатів (FR-004)

Це `meta.total` звичайного `GET /recipes` з тим самим набором параметрів.
Окремого `/recipes/count` навмисно немає: два маршрути з двома запитами
дали б числу під кнопкою «Показати N результатів» шанс розійтися зі
списком, який відкриється за нею.

## Security & edge cases

- Кожна група обмежена 50 опціями: `products` породжує підзапит на кожну
  обрану, і без стелі довгий рядок запиту став би дорогим планом.
- Значення груп валідуються як `uuid`, а не як довільний рядок — інакше
  `?cuisines=italian` тихо повернув би порожню видачу замість 422.
- Невідома вкладка (`?tab=mine`) — 422, а не мовчазне «всі».
- Порожня група (`?diets=`) — це відсутність фільтра, а не фільтр «нічого».

## Verification

- `apps/client-api/test/catalog.db-spec.ts` — довідники повного розміру
  (11/6/6/13 + 15 продуктів), дві кухні розширюють вибірку, другий
  інгредієнт її звужує, група продуктів фільтрує через склад, дві дієти
  дають обидві страви, діапазон рахується на порцію, `800` знімає стелю,
  фільтри діють і на табі «Улюблені».

## Що ще не побудовано

- **FR-005 (скидання)** і лічильник вибраних опцій — клієнтські: сервер не
  тримає стану фільтра.
- **Чи показувати діапазон окремим чипсом** — відкрите питання
  специфікації, чисто інтерфейсне.
- **Чи скидати фільтри при виході з акаунту** — там само; сервер фільтр не
  запамʼятовує, тож будь-яка відповідь — рішення клієнта.
- **Пресети фільтрів** («мої фільтри») поза обсягом специфікації.
- **Повний каталог інгредієнтів у шторці (FR-008)** — це
  `GET /products?q=` без `is_quick_pick`; шторка бере той самий ендпоінт,
  що й пошук.
