# Plan: Recipe search (Пошук інгредієнтів і страв)

## Summary

FR-001, FR-002, FR-003, FR-004, FR-006 і FR-007 — серверна частина: пошук
серед продуктів (`GET /products`) і серед страв (`GET /recipes?q=`), режим
категорії як той самий список із `?categories=`. FR-005 і FR-008
клієнтські (фокус поля, сітка категорій, пауза набору). FR-009 (режим
пікера плану) чекає на домен `meal-plan`.

Власних таблиць не додає.

## Database

Змін немає — читає `products` і `recipes` з
[`../recipes-list/plan.md`](../recipes-list/plan.md).

## API contract

### `GET /products`

**Auth:** `JwtGuard`

`?q=` — підрядок назви мовою читача, без чутливості до регістру.
`?groupId=`, `?page=`, `?limit=`.

**Response 200:**

```json
{
    "data": [
        {
            "id": "…",
            "name": "Помідори",
            "source": "global",
            "group": { "id": "…", "slug": "vegetables", "emoji": "🥦", "name": "Овочі" },
            "caloriesPer100g": 18,
            "proteinPer100g": 0.9,
            "fatsPer100g": 0.2,
            "carbsPer100g": 3.9,
            "servingLabel": "1 шт",
            "servingWeightG": 123,
            "servingCalories": 22,
            "isVerified": true
        }
    ],
    "meta": { "total": 1, "page": 1, "limit": 20, "totalPages": 1 }
}
```

**Дві секції — два запити, а не один «пошук по всьому».** Секції мають
власні лічильники «Результати пошуку: N» (FR-002) і власну пагінацію;
змішана відповідь мусила б нести два підсумки в одному конверті і все одно
розділятися на клієнті.

**`servingCalories` рахує сервер.** Рядок показує «1 шт (123 г) 22 ккал»
(FR-003); хай два екрани не округлюють це двома способами.

**Видимість:** усе каталожне плюс власні продукти цього акаунта. Чужий
користувацький продукт невидимий, доки адмін його не підвищить, — і це
пряме продовження поведінки V1, де пошук приєднував переклад мовою читача.

### `POST /products`

Власний продукт: назва, макроси на 100 г, необовʼязкові група і порція.
**201** з тим самим представленням.

`caloriesPer100g` необовʼязкове — сервер виводить його з макросів
(`calculateCalories`, Atwater). Четверте число, здатне суперечити трьом, з
яких воно виводиться, гірше за його відсутність.

`400` `catalog.unknown-product-group` — неіснуюча група. Перевіряється до
вставки: інакше клієнт отримав би 500 з назвою обмеження, з якої нічого не
зробиш.

**Цей маршрут випереджає свій екран.** Форма додавання продукту належить
`create-dish`, якого ще немає; збудований зараз, бо пікер складу без нього
впирається у стелю каталогу. Позначено як борг у розділі нижче.

### Пошук страв і режим категорії

Це `GET /recipes` з
[`../recipes-list/plan.md`](../recipes-list/plan.md):

- запит — `?q=`;
- режим категорії (FR-006) — `?categories=<id>`, без `q`;
- лічильник «Результати пошуку: N» — `meta.total`.

**Режим категорії не отримав власного маршруту.** Добірка категорії — це
каталог, звужений однією опцією фільтра; `/categories/{id}/recipes` був би
другим описом тих самих рядків з другим набором параметрів, які довелося б
підтримувати синхронно.

**Чи діють фільтри на результати пошуку** — відкрите питання специфікації,
закрите тут ствердно: набір фільтрів спільний (FR-007), і той самий
ендпоінт приймає `q` і групи разом.

## Shared contract

  `PRODUCT_CALORIES_MAX_PER_100G`.

## Security & edge cases

- Крайні пробіли запиту зрізаються схемою, порожній `q` означає «без
  фільтра назви», а не «нічого не знайдено».
- Один символ теж шукає — специфікація цього прямо вимагає; паузу набору
  тримає клієнт.
- Продукт без назви в мові читача і в українській відкидається в SQL — там
  само, де рахується `meta.total`.
- Макрос обмежений 100 г на 100 г, калорійність — 900: чистий жир десь там,
  вище нема нічого їстівного.
- Власний продукт пишеться мовою читача і тільки нею. Це й пояснює, чому
  його не видно акаунту, який читає іншою.

## Verification

- `apps/client-api/test/catalog.db-spec.ts` — пошук продукту частиною
  назви з групою і вагою порції; калорійність власного продукту виводиться
  з макросів (18×4 + 3×4 + 5×9 = 129); власний продукт невидимий іншому
  акаунту; неіснуюча група → 400; пошук страв підрядком без чутливості до
  регістру.

## Що ще не побудовано

- **FR-009 (режим пікера плану з «+»)** — потребує домену `meal-plan`.
- **Картка продукту** за тапом на інгредієнт — домен `product`, дизайну ще
  немає.
- **Окремий порожній стан** — відкрите питання специфікації; сервер віддає
  `meta.total: 0`, текст пише клієнт.
- **`POST /products` без свого екрана** — форма зʼявиться в `create-dish`.
  До того ендпоінт є, але жоден екран його не викликає.
- **Пошук лише за назвами.** За описом і складом — поза цією версією, і
  схема цього ще не готує: індексу під підрядковий збіг немає.
