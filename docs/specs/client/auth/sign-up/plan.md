# Plan: Sign-up (Реєстрація)

## Summary

FR-001…FR-007, FR-009 і FR-014 лягають на `AuthService.register` /
`verifyEmail` / `resendEmailCode` у `apps/client-api/src/modules/auth/` та
таблиці `users` і `otp_codes`. FR-011…FR-013 (реєстрація через провайдера)
описані в [`../sign-in/plan.md`](../sign-in/plan.md) — вхід і реєстрація через
Apple/Google це один механізм. FR-008 (маскування адреси) і FR-010 (згода з
умовами) — клієнтські, бекенду не стосуються.

Політика пароля, TTL коду і ліміт спроб — рішення ADR-0003.

## Database

### Table `users`

| Column                      | Type          | Constraints                                                                           |
| --------------------------- | ------------- | ------------------------------------------------------------------------------------- |
| `id`                        | `uuid`        | PK, `gen_random_uuid()`                                                               |
| `email`                     | `text`        | NOT NULL, UNIQUE (`users_email_unique`)                                               |
| `password_hash`             | `text`        | NULL — поки email не підтверджено (пароль чекає на коді), або акаунт через провайдера |
| `email_verified_at`         | `timestamptz` | NULL, поки код не підтверджено                                                        |
| `created_at` / `updated_at` | `timestamptz` | NOT NULL, `now()`                                                                     |

**Регістронезалежність (FR-001)** досягається нормалізацією на запису:
`emailSchema` у `@dns/validation` робить `trim().toLowerCase()`, тож у базу
потрапляє тільки нижній регістр і звичайного унікального індексу достатньо.
Регістр, який ввів користувач, не зберігається — жоден екран не показує
адресу назад із його капіталізацією.

**Чому `email_verified_at`, а не булеве поле** — дата відповідає на «коли»,
що знадобиться і підтримці, і майбутнім метрикам воронки; булеве поле цю
інформацію втрачає без жодної вигоди.

### Table `otp_codes`

| Column          | Type          | Constraints                                                                        |
| --------------- | ------------- | ---------------------------------------------------------------------------------- |
| `id`            | `uuid`        | PK                                                                                 |
| `user_id`       | `uuid`        | NOT NULL, FK → `users.id` ON DELETE CASCADE                                        |
| `purpose`       | `otp_purpose` | NOT NULL — `email_verification` \| `password_reset`                                |
| `code_hash`     | `text`        | NOT NULL, bcrypt                                                                   |
| `attempts`      | `integer`     | NOT NULL, default 0                                                                |
| `password_hash` | `text`        | NULL; лише `email_verification` — bcrypt пароля реєстрації, якій надіслано цей код |
| `expires_at`    | `timestamptz` | NOT NULL                                                                           |
| `consumed_at`   | `timestamptz` | NULL                                                                               |
| `created_at`    | `timestamptz` | NOT NULL, `now()`                                                                  |

Indexes:

- `otp_codes_user_id_purpose_idx` on `(user_id, purpose)` — пошук чинного коду.
- `otp_codes_one_live_per_purpose` — UNIQUE on `(user_id, purpose)
WHERE consumed_at IS NULL`: живий код флоу — один, це властивість схеми, а
  не домовленість.

**Одна таблиця на два флоу.** Код підтвердження і код відновлення мають
однакову механіку (6 цифр, строк дії, одноразовість, лічильник спроб) і
різняться лише тим, що дає їх споживання — це `purpose`, а не окрема таблиця.

**bcrypt, а не швидкий дайджест.** Простір 6-значного коду — 10⁶; таблиця
SHA-256 хешів реверситься миттєво.

**Спроба резервується до порівняння.** Перевірка коду починається з
`UPDATE otp_codes SET attempts = attempts + 1 WHERE user_id = $1 AND purpose =
$2 AND consumed_at IS NULL AND expires_at > now() AND attempts < 5 RETURNING
code_hash` і лише потім порівнює bcrypt. Раніше лічильник читали, порівнювали
і збільшували після невдачі — N паралельних спроб усі бачили `attempts = 0`,
і ліміт 5 не обмежував нічого. Умовний `UPDATE` серіалізує їх на блокуванні
рядка й перевіряє `attempts < 5` для кожної: більше 5 порівнянь на код не буває
за жодного переплетення запитів.

**Код витрачається один раз.** `UPDATE … SET consumed_at = now() WHERE id = $1
AND consumed_at IS NULL AND expires_at > now() RETURNING …` — у тій самій
транзакції, що й те, що код дає (підтвердження адреси, дозвіл на зміну
пароля). Із двох запитів з правильним кодом рядок отримує рівно один.

**Видача коду — upsert** проти `otp_codes_one_live_per_purpose` (`ON CONFLICT
… DO UPDATE`), а не «видалити й вставити»: два паралельні resend-и не лишають
двох живих кодів. Замінений код отримує **новий `id`**, тож перевірка, що
вже порівнювала старий код, при споживанні за старим `id` не знаходить нічого.

**Пароль реєстрації живе на коді, а не на акаунті.** Див. «Security & edge
cases».

## API contract

### `POST /auth/register`

**Auth:** none (`@Public`), throttle-ключ `register`

**Request body:**

```json
{ "email": "user@example.com", "password": "passw0rd" }
```

| Field      | Type   | Required | Validation                                        |
| ---------- | ------ | -------- | ------------------------------------------------- |
| `email`    | string | yes      | email, нормалізується до нижнього регістру        |
| `password` | string | yes      | ≥ 8 символів, ≤ 72 байтів, ≥ 1 літера і ≥ 1 цифра |

**Response 201** — тіла немає; код надіслано на пошту. Сесія НЕ видається
(FR-003).

**Errors:**

- `409` `auth.email-taken` — акаунт із підтвердженим email уже існує.
- `422` — валідація; `errors[]` називає конкретне невиконане правило, бо поля
  підтвердження пароля у формі немає (FR-002).
- `429` — перевищено ліміт.

**Повторна реєстрація на непідтверджений акаунт не є помилкою.** Акаунт не
змінюється; видається новий код, прив'язаний до нового пароля, відповідь 201.
Це єдиний вихід для того, хто помилився в паролі з першого разу. Пароль стає
паролем акаунту лише тоді, коли підтверджено **саме той код**, який його
несе.

**Подвійне натискання «Зареєструватися».** Обидва запити бачать «нікого
немає» і вставляють; `users_email_unique` відбиває другого, і той продовжує з
акаунтом переможця як звичайна повторна реєстрація — 201, а не 500. Будь-яке
інше порушення унікальності чи зовнішнього ключа, що все ж дійде до
відповіді, `GlobalExceptionFilter` віддає як `409` `common.conflict` (без
назви обмеження і SQL).

**Ця відповідь свідомо розкриває існування акаунту** (FR-009 просить дати
користувачеві змогу перейти до входу). На `/auth/login` і на відновленні
паролю розкриття, навпаки, заборонене — там воно нічого не дає користувачеві.

### `POST /auth/verify-email`

**Auth:** none (`@Public`), throttle-ключ `verify-otp`

**Request body:** `{ "email": "user@example.com", "code": "123456" }`

| Field  | Type   | Required | Validation   |
| ------ | ------ | -------- | ------------ |
| `code` | string | yes      | рівно 6 цифр |

**Response 200:** `{ "data": { "accessToken": "...", "refreshToken": "..." } }`
— користувач автентифікований одразу (FR-007).

**Errors:**

- `400` `auth.invalid-code` — невірний, прострочений, спожитий код, вичерпані
  спроби або адреса без акаунту. Усі п'ять випадків нерозрізненні навмисно.
  Так само відповідає код, замінений resend-ом, поки його перевіряли, і код
  акаунту, який тим часом підтвердили інакше (через Apple/Google).
- `429`.

Підтвердження — одна транзакція `UserRepository.verifyEmailWithCode`: умовне
споживання коду → `UPDATE users SET email_verified_at = now(), password_hash =
<пароль із цього коду> WHERE id = $1 AND email_verified_at IS NULL`. Із
кількох однакових запитів сесію отримує рівно один.

**Власний throttle-ключ** — вимога FR-014: екран запускає перевірку автоматично
на шостій цифрі, тож ендпоінт викликається частіше, ніж якби була кнопка.

### `POST /auth/resend-code`

**Auth:** none (`@Public`), throttle-ключ `send-otp`

**Request body:** `{ "email": "user@example.com" }`

**Response 204** — завжди. Неіснуючий і вже підтверджений акаунт просто не
мають чого надсилати, і сказати про це означало б зробити з ендпоінта
перевірку адрес. Новий код переносить пароль, прив'язаний до попереднього.

Кулдаун 30 с (FR-006) показує клієнт; сервером його не дублюємо — реальний
захист дає rate limit, а таймер це елемент UX.

## Security & edge cases

- Пароль довший за 72 байти **відхиляється**, а не обрізається: bcrypt читає
  лише перші 72 байти, тож два різні довгі паролі стали б взаємозамінними.
  Ліміт саме в байтах — кирилична літера це два, і 40-символьна фраза вже за
  межею.
- Спроба резервується **до** порівняння (умовний `UPDATE`, див. вище), інакше
  паралельні спроби обходять ліміт, і код можна перебирати.
- Видача нового коду замінює попередній одним upsert-ом (FR-006), а унікальний
  частковий індекс гарантує, що в кожен момент живий рівно один.
- **Пароль непідтвердженої реєстрації не пишеться в `users`.** Раніше повторна
  реєстрація безумовно перезаписувала `users.password_hash`: сторонній, що
  знає лише адресу, замінював пароль власника, поки той підтверджував пошту, —
  зокрема записом, що долітав уже після підтвердження. Тепер пароль лежить у
  `otp_codes.password_hash` коду, надісланого цій реєстрації, і переходить в
  акаунт тільки в транзакції, що витрачає саме цей код, умовно на
  `email_verified_at IS NULL`. Акаунти створюються без пароля. Resend і вхід до
  підтвердження переносять пароль на новий код; вхід до підтвердження звіряє
  пароль із ним (нічний sweep цей рядок не видаляє — інакше «підтвердіть пошту»
  перетворилось би на «невірний пароль»); скидання пароля видаляє коди разом із
  цим паролем.
- **Залишковий ризик, який без зміни контракту не закрити:** живий код —
  один, тож реєстрація, що прийшла **після** власника, замінює його код своїм.
  Якщо власник введе саме новий код (він прийде йому на пошту), паролем стане
  пароль того, хто зареєструвався пізніше. Повністю це закриває лише прив'язка
  підтвердження до пристрою, що реєструвався (напр. nonce з `/register`, який
  `/verify-email` мусить повернути), — це зміна контракту для мобільного
  застосунку.
- Підтвердження через Apple/Google непідтвердженого акаунту скидає його пароль
  і коди (див. sign-in plan) — інакше попередня реєстрація стороннього
  переживала б вхід власника через провайдера.
- pino-конфіг редагує `code`, `codeHash`, `password`, `passwordHash` — інакше
  один `logger.log({ user })` відправив би хеш у сховище логів.

## Rollout

- Feature flag: немає.
- Порядок: БД-міграція → деплой `client-api` → реліз мобільного застосунку.
- Міграція гілки `fix/client-auth-races` (`otp_codes.password_hash`,
  `otp_codes_one_live_per_purpose`) генерується під час інтеграції; перед
  створенням індексу треба прибрати дублікати живих кодів (лишити найновіший
  на `(user_id, purpose)`).
- До налаштування `RESEND_API_KEY` листи не надсилаються, а пишуться в лог —
  придатно для дев-стенду, неприйнятно для продакшену.

## Verification

- `apps/client-api/test/auth-otp.db-spec.ts` — ліміт спроб (правильний код
  після вичерпання не працює), інвалідизація попереднього коду при перевидачі,
  одноразовість, повторна реєстрація на підтверджений і непідтверджений акаунт.
- `apps/client-api/test/auth-otp-races.db-spec.ts` — паралельна пачка
  невірних кодів робить рівно 5 порівнянь; правильний код паралельно — одна
  сесія; паралельні resend-и — один живий код.
- `apps/client-api/test/auth-pending-password.db-spec.ts` — пароль не
  пишеться в акаунт до підтвердження; реєстрація після підтвердження нічого не
  змінює; гонка підтвердження з реєстрацією; вхід через провайдера скидає
  непідтверджений пароль; вхід до підтвердження і після sweep-у; resend і
  скидання пароля.
- `apps/client-api/test/auth-registration-races.db-spec.ts` — подвійна
  реєстрація нової адреси (обидві 201, один акаунт) і підтвердженої (усі 409).
- Смоук: `register` → код у логах (stub) → `verify-email` → 200 з парою
  токенів; повторний `register` на ту саму адресу → 409 `auth.email-taken`.
