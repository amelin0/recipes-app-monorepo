# Plan: Profile edit (Редагування профілю)

> **Status is `Approved`, not `Implemented`:** імʼя і фото редагуються, але
> файли, вивантажені й так і не привʼязані до профілю, ніхто не прибирає —
> див. «Що ще не побудовано».

## Summary

FR-003 і FR-005 (редагування імені й похідних ініціалів) покриває
`PATCH /profile`. FR-006 (фото) — теж він: клієнт вивантажує файл через
`POST /uploads` з обсягом `profile-photo` і шле отриманий `publicUrl` у
`photoUrl`. FR-001, FR-002, FR-004 (неактивна кнопка при порожньому полі) —
клієнтські.

## Database

Таблиця `profiles` описана в [`../profile/plan.md`](../profile/plan.md).
`photo_url` зберігає публічний URL файлу в сховищі; сам файл лежить під
ключем `users/<id>/profile-photo/<uuid>-<імʼя>`. Міграції не додає.

## API contract

### `PATCH /profile`

**Auth:** `JwtGuard` (Bearer)

**Request body:**

```json
{ "name": "Олег Чередник" }
```

| Field            | Type           | Required                           | Validation                                        |
| ---------------- | -------------- | ---------------------------------- | ------------------------------------------------- |
| `name`           | string         | ні, але тіло не може бути порожнім | обрізається, 1–100 символів після обрізання       |
| `photoUrl`       | string \| null | ні                                 | URL, отриманий цим користувачем з `POST /uploads` |
| `targetWeightKg` | number \| null | ні                                 | 30–250; `null` знімає ціль                        |

**Response 200:** повний `ProfileView` — той самий, що віддає `GET /profile`,
щоб екран, який повертається назад, не робив другий запит по оновлені
ініціали.

**Errors:**

- `422` — порожнє тіло, порожнє чи саме з пробілів імʼя, довше за 100 символів.
- `400` — `photoUrl` не з нашого сховища, чужий або вивантажений для іншої
  мети (без коду: це баг клієнта, а не стан, з якого є вихід).
- `400` `storage.file-not-uploaded` — дозвіл видано, але файл за ним так і
  не вивантажено. Вихід — вивантажити ще раз і повторити запит.
- `401`.

**Фото перевіряється в сховищі, а не лише за формою URL.** Дозвіл
підписується до вивантаження, тож власний ключ нічого не каже про те, чи
під ним щось лежить; без `HeadObject` профіль міг би вказувати на 404.

**Замінене фото видаляється.** Нове фото чи `photoUrl: null` прибирає файл,
на який профіль вказував до того, — інакше кожна заміна лишала б у сховищі
файл, на який ніхто не посилається.

**`photoUrl`, рівний збереженому, — не зміна:** його не перевіряють удруге і
не видаляють. Форма може надсилати фото, яке показує, разом з імʼям, і файл,
що зник зі сховища, не має заважати зберегти нове імʼя.

**Порожнє імʼя — 422, а не мовчазне збереження.** Кнопка «Зберегти зміни»
неактивна, поки поле порожнє (FR-004), тож порожнє значення не приходить від
екрана: воно означає баг або запит, написаний руками, і обидва заслуговують на
явну відмову.

**Цільова вага редагується тут, хоч її і показує екран прогресу.** Вона
лежить у `profiles.target_weight_kg` з анкети, і фасад під `/progress`, який
писав би в ту саму колонку, дав би одному числу двох власників
([../../progress/metric-logging/plan.md](../../progress/metric-logging/plan.md)).
Схема та сама, що в анкеті, щоб два шляхи до однієї колонки не мали різних
уявлень про допустиме.

**Ліміт у 100 символів** специфікацією не заданий; узятий як розумна межа, щоб
колонка й екран мали передбачуваний максимум.

## Environment variables

Власних не додає; фото йде через `S3_*` модуля сховища. Ключ із
`S3_ACCESS_KEY` мусить мати `s3:GetObject`, `s3:DeleteObject` і
`s3:ListBucket`: без останнього S3 відповідає на відсутній файл `403`, а не
`404`, і перевірка вивантаження стає 500-кою. `scripts/minio-init.sh` дає
всі три.

## Shared contract

- `@dns/validation` — `displayNameSchema`, `updateProfileSchema`. Мобільний
  застосунок переюзає їх у формі, тож «порожнє імʼя» означає те саме на обох
  боках.

## Security & edge cases

- Нормалізація (обрізання пробілів) живе **лише** у схемі. Сервіс приймає вже
  нормалізоване значення, і дублювати `.trim()` у ньому означало б завести два
  місця, які можуть розійтися.
- Профіль оновлюється тільки для власника токена.
- **`photoUrl` приймається лише з трьома умовами:** URL указує на наше
  сховище, ключ лежить під `users/<цей користувач>/profile-photo/`, і файл
  під ним справді є. Сегмент `..`, закодований як `%2F`, і зламана
  percent-послідовність — чужий URL (400), а не 500.
- **Рядок першим, файл другим.** Якби видалення йшло до запису і запис
  упав, профіль указував би на видалений файл. У цьому порядку найгірше —
  файл-сирота.
- **Невдале видалення не валить запит.** Зміна вже збережена; відповісти
  помилкою означало б сказати клієнтові, що її немає. Промах пишеться в лог
  на рівні `error` з ключем файлу — сирота коштує місця, а не битої картинки,
  але повторювані промахи означають, що зі сховищем щось не так.
- **Видаляється лише файл цього користувача з обсягу `profile-photo`.**
  Рядок, записаний до цих перевірок, може вказувати на вкладення звернення
  чи на чужу адресу — таке не чіпаємо: тікет досі на нього посилається.
- **Ключі порівнюються як ключі, а не рядки:** той самий файл, записаний
  іншим percent-кодуванням, не вважається заміною і не видаляється.
- **Два одночасні `PATCH` від одного користувача можуть розминутися.** Якщо
  один надсилає поточне фото, а другий — нове, перший може записати URL,
  який другий щойно видалив. Вікно — між читанням рядка й записом; закрити
  його можна лише серіалізацією всього запиту на користувача, і для
  аватара, який виправляється повторним вивантаженням, це не варте ціни.

  великих літер; `photoUrl` з `POST /uploads` без PUT — 400
  `storage.file-not-uploaded`.

## Що ще не побудовано

**Файли, які так і не привʼязали.** Вивантажене фото, з яким користувач
пішов з екрана, не зберігши, лишається в сховищі назавжди: жоден рядок на
нього не вказує, тож `discardReplaced` про нього не дізнається. Потрібне
правило життєвого циклу бакета або прибирання у воркері, яке звіряє ключі
`profile-photo/` з `profiles.photo_url`.

**Видалення акаунта не чистить фото.** Що саме стирає видалення, вирішує
[ADR-0005](../../../../adr/0005-what-account-deletion-erases.md) (ще
`Proposed`); теку `users/<id>/` у сховищі він поки не згадує.

**Фото страви перевіряється лише на власність.** `POST /recipes` усе ще
кличе `validateOwnership`, а не `validateUpload`, тож страва може вказувати
на файл, якого немає ([../../recipe/create-dish/plan.md](../../recipe/create-dish/plan.md)).
