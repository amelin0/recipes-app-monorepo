# Plan: Weekly list (Список продуктів)

## Summary

FR-001…FR-006 і FR-008 — серверна частина: три таблиці і сім маршрутів під
`/shopping-list`. FR-007 (кнопка «+» у заголовку) і FR-009 (доступність)
клієнтські. Додавання продукту описано в
[`../add-product/plan.md`](../add-product/plan.md).

**Ключове рішення домену: зберігається лише половина списку.** Вручну додані
позиції — рядки в таблиці; імпортовані з плану — сума складу запланованих
страв, порахована на кожному читанні. Саме тому «правила синхронізації з
планом», які специфікація лишає відкритими, писати не доведеться: нічого не
копіювалося, тож нічому й розходитися.

## Database

### Розширення `product_groups`

| Column                | Type      | Опис                                          |
| --------------------- | --------- | --------------------------------------------- |
| `shopping_sort_order` | `integer` | порядок на списку покупок                     |
| `is_recipe_filter`    | `boolean` | чи показує цю групу фільтр рецептів           |

Плюс два нові рядки: `flour` «Мучні» 🥖 і `grains` «Крупи» 🌾.

**Два екрани читають цю таблицю і хочуть від неї різного.** Фільтр рецептів
пропонує рівно шість опцій (recipe-filters FR-002); список групує по семи, з
яких двох фільтр ніколи не бачив (FR-001). Друга таксономія означала б, що
хтось мусить тримати обидві в узгодженні для 272 продуктів — і вони
розійдуться. Тож таксономія одна, а таблиця несе, які групи показує фільтр і
який порядок хоче кожен екран.

**Порядків справді два.** Фільтр починає з овочів, список — із мʼясного. Це
не примха: у фільтрі порядок за частотою вибору, у списку — за маршрутом
магазином.

**Риба і Солодке в макеті списку не названі**, але продукти в них існують —
вони стають аж після семи відомих груп, як FR-001 і вимагає для невідомих.

### Нові таблиці

`shopping_list_items` — вручну додане. PK `(user_id, product_id)`,
`amount_g numeric(9,2)`.

**Один рядок на продукт — це і є SC-003.** Повторне додавання сумується у
вже наявний рядок (add-product FR-009), і «жодних дублікатів» стає
властивістю схеми, а не обіцянкою сервісу.

`shopping_list_marks` — відмітки «куплено». PK
`(user_id, product_id, origin)`, `origin` — енум `manual | plan`.

**Відмітки живуть окремо від позицій, бо половині списку нема що
відмічати:** імпортований рядок існує лише як сума по плану. Наявність
відмітки і є станом — незнята галочка це відсутність рядка, а не `false`.

**Ключ включає походження.** Той самий продукт може стояти в списку двічі —
раз імпортованим, раз доданим руками (add-product FR-009), — і купівля ваших
200 г не має гасити 500 г, потрібних плану.

`shopping_list_settings` — перемикач «Додати з плану», `import_from_plan`
default `true`.

**Власний рядок, а не колонка в `user_settings`:** та таблиця про те, як
застосунок виглядає — тема, одиниці, мова, — і перемикач списку покупок
зробив би її місцем, куди звалюють домени.

### Migrations

- `0009_modern_blonde_phantom.sql` — енум, три таблиці, дві колонки на
  `product_groups`, дві нові групи з перекладами і порядок полиць.

## API contract

### `GET /shopping-list?from=&to=`

**Auth:** `JwtGuard`

Вікно те саме, що показує вкладка плану, і питається так само.

```json
{
    "data": {
        "importFromPlan": true,
        "groups": [
            {
                "group": { "id": "…", "slug": "vegetables", "emoji": "🥦", "name": "Овочі" },
                "items": [
                    { "productId": "…", "name": "Морква", "origin": "plan", "amountG": 200, "calories": 82, "purchased": false }
                ]
            },
            { "group": null, "items": [{ "productId": "…", "name": "Домашній сир", "origin": "manual", "amountG": 200, "calories": 258, "purchased": false }] }
        ],
        "visibleCount": 2
    }
}
```

**`group: null` — це «Інше».** Продукт без групи, а не група з назвою
«інше»: вигадувати рядок довідника заради відсутності — значить дозволити
комусь його перекласти й посортувати.

**`visibleCount` рахує сервер.** Це бейдж таба (FR-008), і SC-004 вимагає,
щоб він завжди дорівнював кількості рядків. Число, пораховане там же, де
зібрані рядки, розійтися з ними не може.

**Порожні групи не віддаються** (FR-001) — картка-група без рядків це
порожнє місце на екрані.

**Вікно потрібне, бо імпортована половина — це сума саме за ці дні.** Список
«на тиждень» без дат мусив би вгадувати, який тиждень, — те саме, чого я
уникнув у плані.

### `POST /shopping-list/items`

`{ "productId": "…", "unit": "piece", "value": 2 }` → **201**.

Одиниці й межі — `SHOPPING_UNIT_LIMITS`; переведення в грами —
`SHOPPING_UNIT_GRAMS`. Описано в [`../add-product/plan.md`](../add-product/plan.md).

### `DELETE /shopping-list/items/{productId}`

**204.** `404` `shopping-list.item-not-found` — і коли рядка немає, і коли
рядок імпортований: у нього немає власного рядка, щоб його видаляти.

**Специфікація каже, що видалення позиції «в цій версії не передбачено».**
Побудовано все одно: без нього і без автоматичного очищення список тільки
росте. Кнопки в макеті немає — це борг дизайну, не сервера.

### `PUT` / `DELETE /shopping-list/items/{origin}/{productId}/purchased`

**204** обидва, обидва ідемпотентні (FR-003).

**Підресурс, а не `toggle`** (ADR-0004): повтор у магазині з поганим
звʼязком не має знімати щойно поставлену галочку.

**`origin` у шляху, бо ключ відмітки складений.** Це не прикраса: без нього
одна галочка гасила б два рядки.

### `DELETE /shopping-list`

**204** — прибирає вручну додані рядки й усі відмітки. План не чіпає:
список покупок не те місце, де живуть страви.

### `PUT` / `DELETE /shopping-list/plan-import`

Перемикач «Додати з плану» (FR-004), булевий стан підресурсом.

**Вимкнення нічого не видаляє** (FR-005): імпортовані рядки перестають
приходити, а їхні відмітки лишаються на місці й повертаються разом із ними.
Це виходить само собою — відмітка не залежить від рядка, якого не існує.

## Security & edge cases

- Кожне читання і кожен запис обмежені власником токена.
- Додати можна лише продукт, який цей акаунт бачить: чужий користувацький
  продукт дає 404, а не мовчазне додавання і показ його назви.
- Продукт, якого акаунт більше не бачить, зникає з рядка, а не малюється
  безіменним.
- Відмітки навмисно **не** прибираються, коли рядок зникає зі списку:
  FR-005 прямо вимагає, щоб галочка пережила вимкнення перемикача, а зміна
  плану з погляду списку — та сама ситуація. Ціна — рядок на продукт на
  акаунт; явне очищення його прибирає.
- Кількість — завжди грами. Обʼєм (мл) з FR-002 чекає, доки продукти
  навчаться його нести: склад рецепта теж лише в грамах (ADR-0006).

## Verification

- `apps/client-api/test/shopping-list.db-spec.ts` — 18 тестів: порожній
  список, переведення одиниць, злиття з сумуванням і зняттям галочки,
  видалення й відмова, сума складу по продуктах і по двох стравах, вікно,
  перемикач ховає імпортоване і зберігає ручне, галочки повертаються,
  ручний і імпортований рядок того самого продукту окремі, галочка одного
  не чіпає інший, очищення не чіпає план, порядок полиць, продукт без групи.
- `packages/validation` — 5 тестів схем.

## Що ще не побудовано

- **Життєвий цикл списку** (відкрите питання) закрито як «ніколи сам»:
  список чистить тільки людина. Автоматичне очищення на межі тижня
  вимагало б від сервера рішення, де тиждень починається, і забирало б
  список у неділю ввечері в того, хто ще не сходив у магазин.
- **Обʼємні продукти (мл)** — потребують одиниці на продукті.
- **Редагування кількості вже доданої позиції** — поза обсягом
  специфікації; поки що це видалити й додати наново.
- **Бейдж таба** віддається як `visibleCount`; малює його клієнт.
