# Plan: Meal plan (Вкладка «План»)

## Summary

FR-001, FR-002, FR-003, FR-004, FR-007, FR-008 і FR-010 — серверна частина:
одна таблиця `meal_plan_items` і пʼять маршрутів під `/meal-plan`. FR-005
(«Змінити ціль») веде в наявний `PUT /nutrition/goal`. FR-011 (пошук у
режимі додавання) — це `GET /recipes` з
[`../../recipe/recipe-search/plan.md`](../../recipe/recipe-search/plan.md).
FR-012 (екран успіху після створення страви) — клієнтський; сама страва
створюється через `POST /recipes`.

**FR-006 переосмислено 2026-09-08.** Домен `shopping-list` з'явився у
зрізі 11 — і виявилося, що будувати нема чого: список **сумує план на
кожному читанні**, тож запланована страва вже в ньому. Замість кнопки
«додати» день плану віддає `importsIntoShoppingList` — стан перемикача
«Додати з плану». Специфікація й сценарії переписані під це.

Статус лишається `Approved` через FR-009 (редагування прийому): екрана
немає в дизайні.

## Database

### Нова таблиця `meal_plan_items`

| Column       | Type          | Constraints                                  |
| ------------ | ------------- | -------------------------------------------- |
| `id`         | `uuid`        | PK                                           |
| `user_id`    | `uuid`        | NOT NULL, FK `users`, ON DELETE CASCADE      |
| `plan_date`  | `date`        | NOT NULL — день у календарі користувача      |
| `slot`       | `meal_slot`   | NOT NULL — енум уже існує з домену nutrition |
| `recipe_id`  | `uuid`        | NOT NULL, FK `recipes`, **ON DELETE CASCADE**|
| `sort_order` | `integer`     | NOT NULL, порядок у межах прийому            |
| `created_at` | `timestamptz` | NOT NULL                                     |

Індекс `meal_plan_items_user_date_idx` на `(user_id, plan_date)` — усі
читання домену йдуть саме цим шляхом.

**Посилання, а не зліпок — протилежність `meal_log_entries`.** Запис у
журналі це чек про те, що зʼїли, і він мусить читатися правильно завжди,
тому копіює числа. Позиція плану — намір щодо страви, яка ще існує: якщо
рецепт відредагували, план має йти за ним, а якщо видалили — готувати нема
чого. Звідси зовнішній ключ і звідси каскад.

**Порцій у таблиці немає.** Пікер додає страву одним тапом і кількості не
питає (FR-010), тож колонка була б числом, якого не збирає жоден екран.
Одна позиція означає одну порцію.

- `0008_mean_peter_quill.sql` — таблиця, два зовнішні ключі, індекс.

## API contract

### `GET /meal-plan?from=&to=`

**Auth:** `JwtGuard`

Вікно до 31 дня. Повертає **кожен** день діапазону, включно з порожніми.

```json
{
    "data": [
        {
            "date": "2026-05-18",
            "slots": [
                { "slot": "breakfast", "items": [] },
                {
                    "slot": "lunch",
                    "items": [{ "id": "…", "recipe": { "id": "…", "title": "Обід", "perServing": { "calories": 700 } } }]
                },
                { "slot": "dinner", "items": [] },
                { "slot": "snack", "items": [] }
            ],
            "planned": { "calories": 700, "proteinG": 20, "fatsG": 10, "carbsG": 40 },
            "goal": { "calories": 2000, "proteinG": 150, "fatsG": 67, "carbsG": 200 },
            "outcome": "under"
        }
    ]
}
```

**Діапазон дат, а не номер тижня.** Де починається тиждень — справа
клієнта; сервер інакше мусив би вгадувати перший день тижня локалі й для
когось помилятися. `?week=` із карти шляхів так і не знадобився.

**Вікно приходить цілим, разом зі стравами.** Смузі тижня потрібен стан
кожного дня, а вибраному дню — його страви; тягнути це окремо означало б
робити кожен тап по смузі поїздкою на сервер, чого SC-001 прямо не
дозволяє.

**Чотири прийоми є завжди, навіть порожні.** «Не заплановано» — це стан
слота, а не його відсутність (FR-002); клієнт не має відновлювати структуру
дня з того, чого немає.

**`outcome` рахує сервер** — тим самим допуском ±10 %
(`DAILY_TARGET_TOLERANCE`, [ADR-0007](../../../../adr/0007-daily-norm-formulas.md)),
яким прогрес фарбує день. Два різні визначення «приблизно в нормі»
дозволили б вкладці плану і графіку прогресу розійтися про той самий день.

**`outcome: null`, коли цілі немає або нічого не заплановано.** Порожній
день — це не вирок про день, і поради під зведенням для нього немає (FR-004).

**Окремого `GET /meal-plan/days/{date}` немає.** Діапазон уже віддає день
цілком, а мутації повертають змінений день — другий маршрут описував би ті
самі рядки вдруге.

### `POST /meal-plan/days/{date}/items`

`{ "slot": "lunch", "recipeId": "…" }` → **201** з усім днем.

`404` `meal-plan.recipe-not-found` — страви немає або вона чужа власна.

**Відповідь — день, а не створена позиція.** Підсумки дня і його стан проти
цілі рахує сервер, тож клієнт не може перерахувати їх, не несучи допуск у
собі. Те саме стосується `DELETE`.

### `DELETE /meal-plan/days/{date}/items/{itemId}`

**200** з днем, перерахованим після видалення (FR-007).
`404` `meal-plan.item-not-found`.

### `DELETE /meal-plan/days/{date}`

**200** з порожнім днем.

### `POST /meal-plan/days/{date}/copy`

`{ "targetDates": ["2026-05-19", "2026-05-20"] }` → **200** зі списком
змінених днів.

**Копіювання перезаписує цільовий день, а не доповнює його** (закрито
відкрите питання специфікації). «Копіювати» означає, що ціль стає такою ж,
як джерело; доповнення на вже запланованому дні тихо подвоїло б калорії, а
шторка, яка це запускає, відкоту не має.

**Порожній день копіювати заборонено** — `400`
`meal-plan.nothing-to-copy`. Інакше це очистило б кожен день, на який його
націлили: руйнівна дія у вбранні нешкідливої.

**День не можна скопіювати сам на себе** — `400`
`meal-plan.source-among-targets`.

**Дієслово в шляху, чого ADR-0004 загалом не дозволяє.** Це не зміна стану
одного ресурсу, а операція над кількома; `PUT` на кожен цільовий день окремо
дав би N шансів зупинитися на півдорозі. Копіювання виконується однією
транзакцією.

## Security & edge cases

- Кожне читання і кожен запис обмежені власником токена; позиція плану
  видаляється з фільтром по `user_id` у самому `WHERE`.
- Страву можна запланувати лише таку, яку цей акаунт бачить: чужа власна
  страва дає 404, а не мовчазне додавання.
- Вікно плану — рік у минуле і рік у майбутнє, ширше за вікно журналу і з
  протилежної причини: планувати наступний місяць це сенс планування, а
  **записати** зʼїдене наступного місяця — зламаний годинник.
- Діапазон обмежений 31 днем: без стелі один запит зібрав би десятиліття
  по дню.
- Порядок у прийомі присвоюється в тому ж операторі, що й вставка, тож два
  одночасні тапи не займуть одну позицію.
- Страва, яку акаунт більше не бачить, зникає зі слота, а не малюється
  порожнім рядком.
- **Виправлено принагідно:** `Date.parse` для рядка, який ISO-граматика
  відкидає, вмикає легасі-парсер, тож `2026-02-31` повертався як 3 березня
  замість `NaN`, і `logDateSchema` таку дату приймала. Перевірка тепер
  проганяє дату назад у рядок і порівнює. Це стосується всіх доменів, що
  беруть дату від клієнта.

## Що ще не побудовано

- **FR-006 (список покупок)** — зроблено інакше, ніж просив макет: не
  кнопкою, а станом. SC-003 вимагав, щоб «у списку» завжди збігалося зі
  списком — тепер це виконується конструктивно, бо `importsIntoShoppingList`
  віддає той самий перемикач, який вирішує вміст списку. Прапорця в плані
  не зберігається.
- **FR-009 (редагування прийому)** — відкрите питання специфікації, дизайну
  немає.
- **Інгредієнт як позиція плану** — вкладка «Інгредієнти» в пікері поки не
  має контракту порції (відкрите питання специфікації); без відповіді на
  «скільки грамів за замовчуванням» калорійність позиції була б вигаданою.
- **Пороги кольорів смужок БЖВ** — сервер віддає `planned` і `goal`; стан
  калорій рахує (`outcome`), а фарбування окремих макросів лишається
  клієнту, доки продукт не назве для них пороги.
- **Автогенерація плану** — поза обсягом специфікації.
