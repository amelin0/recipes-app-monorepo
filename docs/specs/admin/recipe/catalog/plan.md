# Plan: Recipe catalogue (Каталог рецептів)

## Summary

Схема вже є: `recipes`, `recipe_translations`, `recipe_ingredients`,
`recipe_steps` (+ переклади й зв'язок з інгредієнтами), `recipe_diets` —
усе побудоване під клієнтський домен і нових таблиць **не потребує**. Цей
зріз — це CRUD поверх них (FR-006…FR-013), парсер CSV (FR-001…FR-005) і
одне нове поле для дедуплікації.

Найбільше роботи не в ендпоінтах, а в **розриві між тим, що очікує наявний
веб, і тим, що є в схемі**. Веб писався під V1; нижче для кожної
розбіжності — рішення від 2026-09-07 і причина.

| Веб очікує | У нас | Рішення |
|---|---|---|
| `/admin/recipes`, snake_case, плоска відповідь | ADR-0002/0004 | правимо веб |
| `tags` / `tag_ids` | три довідники | плоский фасад `{id, kind, name}` |
| `{ingredient_id, amount, unit}` | тільки грами | грами; `unit` не приймаємо |
| `cooking_instructions: string[]` | `recipe_steps` зі структурою | структура |
| файл на `/admin/upload/recipe-image` | presigned URL | presigned |

## Database

Нових таблиць немає. Одна зміна і два похідні читання.

### Зміна: `recipes.import_key`

| Column | Type | Constraints |
|---|---|---|
| `import_key` | `text` | NULL, UNIQUE коли не NULL |

FR-004 неможливий без ключа: у рецепта немає природного унікального поля
(назви повторюються, і англійська назва — це переклад, а не ідентичність).
`import_key` — стовпчик із CSV, який задає автор; повторний імпорт того
самого ключа **оновлює** рядок замість створювати другий.

Частковий унікальний індекс `where import_key is not null`: страви,
створені руками або користувачем, ключа не мають, і NULL не повинні
конфліктувати між собою.

Мок-сід (`5eed%`) ключів не має — він видаляється, а не мігрує.

### Похідні числа

- `favorites_count` (FR-013) — **не колонка**, а `count(*)` з
  `recipe_favorites` у запиті списку. Лічильник-колонка вимагав би
  тригерів або оновлення на кожне вподобання, а це число потрібне лише
  адмінці й лише приблизно.
- Харчова цінність (FR-014) лишається **збереженою** в `recipes`, як і
  зараз. Причина в коментарі до схеми: правка макросів продукту не має
  тихо змінювати цифру в чужому щоденнику харчування.

### Migrations

- `0013_recipe_import_key.sql` — колонка + частковий унікальний індекс.

## API contract

Базовий шлях `/api/v1`, без `/admin` (ADR-0002), конверт `{data}` і
camelCase (ADR-0004). Усі маршрути — Bearer + роль ADMIN/SUPER_ADMIN
(FR-015).

### `GET /api/v1/recipes`

Query: `search`, `categoryId`, `cuisineId`, `dietIds` (кома), `page`,
`limit` (за замовчуванням 20, максимум 100), `language` (за замовчуванням
`uk`).

**Response 200:** `{ "data": [...], "meta": { page, limit, total } }` —
через `Paginated`, як у client-api.

```json
{ "id": "…", "photoUrl": null, "title": "Грецький салат",
  "calories": 783, "proteinG": 22.92, "fatsG": 63.09, "carbsG": 37.5,
  "servings": 2, "cookTimeMinutes": 15, "favoritesCount": 12,
  "category": { "id": "…", "slug": "salads" },
  "cuisine": { "id": "…", "slug": "greek" },
  "diets": [ { "id": "…", "slug": "vegetarian" } ],
  "updatedAt": "…" }
```

Пошук — по `recipe_translations.title` обраної мови, без урахування
регістру. Це підрядковий скан: btree його не обслуговує, і на тисячі
рецептів це нормально. Trigram-індекс — коли перестане бути нормально, і
не раніше.

### `GET /api/v1/recipes/:id`

Повна страва: усі переклади, склад із назвами продуктів, кроки з
тривалістю й інгредієнтами. Одна відповідь на все — у веба був окремий
`/full`, але два майже однакові представлення розходяться.

### `POST /api/v1/recipes` · `PATCH /api/v1/recipes/:id`

```json
{
  "photoUrl": null,
  "servings": 2,
  "cookTimeMinutes": 15,
  "categoryId": "…",
  "cuisineId": "…",
  "dietIds": ["…"],
  "translations": [ { "language": "uk", "title": "…" } ],
  "ingredients": [ { "productId": "…", "amountG": 250, "sortOrder": 0 } ],
  "steps": [
    { "stepNumber": 1, "durationMinutes": 8,
      "translations": [ { "language": "uk", "title": "…", "description": "…" } ],
      "ingredientIndexes": [0, 1] }
  ]
}
```

| Field | Required | Validation |
|---|---|---|
| `translations` | так | ≥1; `uk` обов'язкова — вона фолбек у `coalesce` |
| `ingredients` | так | ≥1; `productId` існує; `amountG` > 0 |
| `steps` | ні | `stepNumber` унікальні й послідовні з 1 |
| `dietIds` | ні | усі існують |
| `categoryId`, `cuisineId` | ні | існують; **по одному** (FR-011) |
| `photoUrl` | ні | має бути з нашого сховища, не довільний URL |

`ingredientIndexes` посилається на позицію в `ingredients` цього ж запиту,
бо id інгредієнтів ще не існує на момент створення. Схема зв'язує крок із
**рядком складу**, а не з продуктом: чип означає «ті 250 г помідорів із цієї
страви», і посилання на продукт втратило б кількість.

`PATCH` частковий, але `ingredients` і `steps` — **заміна цілком**, не
злиття. Часткове злиття колекцій із власним порядком і зв'язками — це
джерело тихих розсинхронів; редактор надсилає повний список (FR-007).

Макроси (`calories`, `proteinG`…) **не приймаються з запиту**: сервер
рахує їх зі складу як `Σ(per100g × amountG / 100)`. Форма в адмінці показує
пораховане, а не збирає його з рук. Це закриває один із двох варіантів
відкритого питання специфікації — див. **Open Questions** там.

### `POST /api/v1/recipes/bulk-delete`

`{ "ids": ["…"] }` → `{ "data": { "deleted": 3 } }` (FR-008).

Не `DELETE` з тілом: HTTP його дозволяє, а проксі й клієнти регулярно
викидають. `POST` на дію — менш красиво і більш передбачувано.

### `GET /api/v1/tags`

Плоский фасад над трьома довідниками (рішення від 2026-09-07):

```json
[ { "id": "…", "kind": "category", "slug": "salads",     "name": "Салати" },
  { "id": "…", "kind": "cuisine",  "slug": "greek",      "name": "Грецька" },
  { "id": "…", "kind": "diet",     "slug": "vegetarian", "name": "Вегетаріанське" } ]
```

⚠️ Фасад **не** стирає кратність. `POST /recipes` приймає `categoryId`,
`cuisineId`, `dietIds` окремо саме тому, що плоский `tagIds` дозволив би
надіслати дві кухні, і ловила б це валідація замість форми. Фасад
призначений для **читання** — щоб адмінка малювала один список міток, — а
не для запису.

### `GET /api/v1/products` (для складу)

Пошук продуктів для форми складу (FR-010). Повний домен продуктів — окремий
зріз; тут потрібен лише пошук за назвою з поверненням макросів.

### `POST /api/v1/uploads/recipe-image`

```json
{ "fileName": "salad.jpg", "contentType": "image/jpeg", "sizeBytes": 482910 }
```

→ `{ "data": { "uploadUrl": "…", "fileUrl": "…", "expiresIn": 900 } }`

Байти йдуть у сховище повз API (рішення від 2026-09-07), тим самим
механізмом, що в client-api. Наслідок: nginx лишається з
`client_max_body_size 2m`, а воркер Node не тримає файли в пам'яті.

Після завантаження — `PATCH /recipes/:id { photoUrl }`. Осиротілі файли
(завантажили, рецепт не зберегли) — відома ціна presigned-підходу; прибирає
їх окреме завдання, якого поки немає.

### `POST /api/v1/recipes/import`

`multipart/form-data`, поле `file` — CSV. Тут файл **справді** проходить
через API: він маленький (500 рядків ≈ 200 КБ), і його треба розібрати, а
не покласти.

**Response 200:**

```json
{ "data": {
  "created": 8, "updated": 2, "skipped": 2,
  "errors": [ { "row": 14, "importKey": "greek-salad",
                "message": "продукт «Фета» не знайдено в каталозі" } ] } }
```

Відповідь `200` навіть коли є помилки: частковий успіх — це **очікуваний**
результат (FR-003), а не збій запиту.

**Errors:**

- `422` — файл не CSV, немає обов'язкових колонок, порожній. Тут падає весь
  файл, бо проблема не в рядку (edge case зі специфікації).
- `413` — файл більший за ліміт.

## Формат CSV

Один рядок = один рецепт. Мультизначні поля — крапка з комою всередині
клітинки; так файл лишається редагованим у Excel і Google Sheets, куди він
і повертається до шеф-редактора.

| Колонка | Обов'язкова | Приклад | Примітки |
|---|---|---|---|
| `import_key` | так | `greek-salad` | ключ дедуплікації (FR-004) |
| `title_uk` | так | `Грецький салат` | |
| `title_en` | ні | `Greek salad` | |
| `category` | ні | `salads` | slug довідника |
| `cuisine` | ні | `greek` | slug, **один** |
| `diets` | ні | `vegetarian;gluten-free` | slugs через `;` |
| `servings` | так | `2` | ціле > 0 |
| `cook_time_minutes` | ні | `15` | |
| `photo_url` | ні | | має бути з нашого сховища |
| `ingredients` | так | `Tomatoes:250;Feta:120` | `англійська_назва:грами` |
| `steps_uk` | ні | `Наріжте овочі\|Додайте фету` | кроки через `\|` |
| `steps_en` | ні | | має збігатися кількістю зі `steps_uk` |
| `step_durations` | ні | `8;3` | хвилини, у порядку кроків |

**Продукти шукаються за англійською назвою** і мусять уже існувати
(FR-005). Створення продукту на льоту дало б рядок без макросів, а страву —
нерахованою; краще впасти з поясненням, яке редактор виправить сам (SC-002).

**Одиниці — тільки грами.** Колонки `unit` немає, і це не спрощення:
`recipe_ingredients` не має такої колонки свідомо (див. коментар до схеми).
«1 склянка» — рядок, макроси якого ніхто не порахує, у страві, чиї підсумки
все одно мусять зійтися.

**Кроки без прив'язки до інгредієнтів.** CSV не витягне
`ingredientIndexes`, не перетворившись на другий формат усередині першого.
Імпортована страва отримує кроки без чипів; чипи додаються руками у формі,
де вони й потрібні.

**Транзакція на рецепт, не на файл.** Один рецепт — одна транзакція: рядок
із помилкою відкочується цілком, решта файлу продовжується (FR-003). Одна
транзакція на файл означала б, що 499 добрих рецептів відкотяться через
500-й.

## Shared contract

`@dns/shared-types` — `AdminRecipeListItem`, `AdminRecipeDetail`,
`ImportReport`, `TagKind`. `@dns/validation` — `createRecipeSchema`,
`updateRecipeSchema`, `importQuerySchema`; веб валідує форму тими самими
схемами.

Клієнтські типи рецепта **не** переиспользуються: адмінка бачить поля
(`importKey`, `favoritesCount`), яких мобільному застосунку знати не треба.

## Security & edge cases

- **Усі маршрути за роллю** ADMIN/SUPER_ADMIN (FR-015); публічних немає.
- **CSV-ін'єкція.** Клітинка, що починається з `=`, `+`, `-`, `@`, у Excel
  виконується як формула. Ми CSV **читаємо**, але ці ж значення потім
  потрапляють у назви страв і повертаються редактору експортом. Значення
  зберігаються як є, екранування — на боці експорту, коли він з'явиться.
- **Ліміт розміру** файлу і `IMPORT_MAX_ROWS` — щоб один запит не з'їв
  пам'ять воркера.
- **`photoUrl` не довільний URL** — тільки префікс нашого сховища. Інакше
  адмінка стає засобом вставити чуже посилання в мобільний застосунок.
- **Імпорт не паралельний сам із собою** на одному ключі: два одночасні
  завантаження того самого файлу впораються завдяки унікальному індексу на
  `import_key`, а не завдяки везінню.
- **Видалення страви** зачіпає `meal_plan_items`, `recipe_favorites`,
  `shopping_list`. Поведінка визначена FK, але **продуктове** рішення —
  відкрите питання специфікації; до його закриття видалення обмежене
  стравами, яких немає в жодному плані.

## Rollout

- Feature flag: немає.
- Порядок: міграція → деплой admin-api → правки `apps/web` → Vercel.
- Мок-сід (`5eed%`) видаляється **після** першого успішного імпорту, не
  раніше: інакше каталог порожній у проміжку. Команда — у
  [`infra/prod/README.md`](../../../../../infra/prod/README.md).
- Клієнтський API не змінюється: та сама схема, ті самі відповіді.

## Verification

- Unit: парсер CSV — розділювачі, порожні необов'язкові колонки, невідомий
  slug, невідомий продукт, неузгоджена кількість кроків і тривалостей.
- DB-тести: створення з кроками й чипами; `PATCH` замінює склад цілком;
  повторний імпорт того самого `import_key` оновлює, а не дублює (FR-004);
  рядок з невідомим продуктом не створює нічого, а сусідні створюються
  (FR-003, FR-005).
- Тест на **порахований підсумок**: макроси створеної страви дорівнюють
  сумі складу — той самий інваріант, який тримає мок-сід.
- Смоук: імпортувати файл на 3 рецепти, з них один зіпсований → `created:2`,
  один `errors[]`; знайти рецепт пошуком; видалити.
- Метрики: тривалість `/recipes/import` у Grafana. SC-001 — 500 рядків за
  60 с; регресія тут означає N+1 у пошуку продуктів.
