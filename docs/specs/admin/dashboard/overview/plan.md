# Plan: Dashboard overview (Головна панелі)

## Summary

Тільки читання: жодної нової таблиці, жодної колонки, жодної міграції.
Агрегати поверх того, що вже є (FR-001…FR-011).

Рішення власника продукту від 2026-09-08:

| Питання | Рішення |
|---|---|
| Що на головній | **Операційний огляд**: ріст + розмір + сигнали роботи |
| Статистика обраного | **Тільки числа** — без переліку людей |
| Розріз за країнами | **Немає** — поля не існує ніде |

## Database

Змін немає. Джерела агрегатів:

| Показник | Звідки |
|---|---|
| Реєстрації по днях | `users.created_at` |
| Мови | `user_settings.language`, `left join` — незадана окремо |
| Акаунти, заблоковані | `users`, `users.blocked_at` |
| Активні підписки | `subscriptions.status = 'active'` |
| Страви каталогу | `recipes.source = 'global'` |
| Продукти | `products`, **без** заархівованих |
| Неперевірені користувацькі | `products.source = 'custom' and is_verified = false` |
| Нові звернення | `feedback.status = 'new'` |
| Прострочені видалення | `account_deletion_requests`, активні з `scheduled_for <= now()` |
| Обране | `recipe_favorites` |

Індексів не додаємо: усе це `count(*)` по таблицях у тисячі рядків, і
жоден із запитів не сканує більше, ніж уже сканують сторінки, які ті самі
числа показують.

## API contract

Базовий шлях `/api/v1`, конверт `{data}`, camelCase (ADR-0002/0004). Обидва
маршрути під Bearer + ADMIN/SUPER_ADMIN (FR-012).

### `GET /api/v1/stats/overview?days=7`

`days` — `7 | 30 | 90` (FR-004); інше відхиляється, бо кнопок рівно три, а
довільний діапазон обіцяв би те, чого екран не вміє.

```json
{ "registrations": { "total": 42,
                     "byDate": [ { "date": "2026-09-01", "count": 3 } ],
                     "byLanguage": [ { "language": "uk", "count": 900 },
                                     { "language": null, "count": 12 } ] },
  "users": { "total": 1200, "blocked": 3, "withActiveSubscription": 87 },
  "catalogue": { "recipes": 120, "products": 340, "unverifiedCustomProducts": 5 },
  "queues": { "newTickets": 4, "overdueDeletions": 2 } }
```

**Один запит, а не п'ять.** Це один екран; п'ять окремих ендпоінтів
малювали б його частинами і давали б п'ять станів завантаження там, де
насправді один.

`byDate` **містить кожен день періоду**, включно з нульовими (FR-005):
пропущений день зсуває стовпчики і бреше про форму росту. Робить це
`generate_series` з `left join`, а не JavaScript, який дозаповнює дірки —
інакше «які дні існують» вирішували б у двох місцях.

`byLanguage` рахує акаунти без налаштувань як `language: null` (FR-006).
`inner join` тихо викинув би їх, і сума перестала б сходитися із загальною
кількістю — розбіжність, яку ніхто не помітив би, доки не почав рахувати.

День — **доба UTC**. Не тому, що це найкраще, а тому, що це має бути
однозначно; локальна доба зробила б межу різною для різних читачів.

### `GET /api/v1/stats/favorites?page&limit`

Страви за кількістю додавань в обране, від найпопулярнішої:

```json
{ "id": "…", "name": "Грецький салат", "photoUrl": "…",
  "calories": 320, "favorites": 18,
  "byLanguage": [ { "language": "uk", "count": 12 } ] }
```

**Переліку людей немає** (FR-011), і це рішення: що людина зберігає в
обране — це персональні дані, а редакторові контенту потрібні числа, а не
імена. Та сама лінія, що в картці користувача, куди не потрапляє анкета про
тіло.

Розріз за мовами рахується **одним запитом на сторінку**, а не запитом на
страву: двадцять рядків — це двадцять зайвих звернень, які ніхто не помітить
на локальній базі й помітять усі на справжній.

## Security & edge cases

- **Обидва маршрути за роллю** (FR-012).
- **Порожня база — нулі, не помилка** (SC-004): усі агрегати повертають `0`,
  а `byDate` — ряд нулів.
- **Числа мають збігатися зі сторінками** (FR-009): лічильник продуктів
  рахує **без** заархівованих, як і `GET /products`; нові звернення — той
  самий предикат, що `status=new`; прострочені видалення — той самий, що
  `deletion=overdue`.
- **Смаки не персоналізуються** — жоден із двох маршрутів не віддає id
  користувача.

## Verification

- DB-тести: `byDate` містить кожен день періоду і нулі там, де реєстрацій не
  було; акаунт без налаштувань потрапляє в `language: null`; заархівований
  продукт не рахується; лічильники черг збігаються з фільтрами відповідних
  списків; порожня база дає нулі.
- Тест на порядок: страви обраного йдуть від найпопулярнішої.
- Тест на межу: `days=1` відхиляється.
